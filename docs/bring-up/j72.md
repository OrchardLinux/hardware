# iPad Air 1 Cellular (J72) RAM bring-up

Status recorded on 2026-10-31 for one owner's iPad. This field report records
working hardware paths and measurements for a future J72 device contribution.
The results come from a local development kernel and RAM overlays. They do
not establish that this Orchard revision builds or boots a J72 image, and
this report does not register a device descriptor or an installation path.

## Development source included in this draft

The [J72 source snapshot](../../experiments/j72/README.md) includes the measured
SPI controller correction, full touch worker and decoder, HDQ/UART battery
frontend and supporting patches, read-only PMIC observer, tested 425 mA
one-shot worker, and synthetic tests. Source hashes and original notices are
included. Apple firmware and calibration inputs are excluded.

This is an inactive development snapshot for implementation review at the
author's request. It is outside the applied patch series and changes no
supported device. It still needs conversion to the normal form required by
[CONTRIBUTING.md](../../CONTRIBUTING.md); the concrete work is listed in
[the integration plan](../../experiments/j72/UPSTREAM-PLAN.md). Desktop patches
remain in the linked companion repository for a separate omarchy-a change.

## Touch findings useful to a native port

### SPI completion was insufficient evidence of packet delivery

The original S5L transport could report a completed upload while the touch
controller returned `0x4cb1` instead of the expected data ACK, `0x4bc1`.
Changing packet sizes, padding and receive accounting did not resolve that.

Sampling the GPIO input buffers while transmitting a slow known pattern,
with reset asserted and touch power off, exposed two problems in that tested
controller implementation: AUTO_TX generated clocks with constant MOSI rather
than the queued payload, and the bit-order flag mapping was reversed.
A temporary GPIO SPI path accepted the unchanged firmware packet. Hardware SPI
then reproduced acceptance by disabling AUTO_TX for explicit payloads,
starting before queuing bytes, draining RX and bounding outstanding data to
the FIFO depth. The corrected Linux SPI API path also received `0x4bc1`.

This identifies a transport failure in that implementation; it does not assign
a universal meaning to the earlier return code. Future changes must use
compatible-selected controller data and preserve other SoCs' behavior.

### Application readiness did not establish contact scanning

J72 requires its N1 startup/calibration personality and the address-bearing
Z2 execute path. Firmware acceptance, checksummed device information and
matching surface metrics all passed before any finger reports appeared.
The ROM query identified C1F15; application information reported interface
version 1 and maximum packet size 2,454.

The decisive contact test corrected an omitted shared analog-power enable.
The tested D2089 register `0x84` changed from `0x04` to `0x07`, including the
shared low two bits. The voltage setting at `0x398` remained `0x14`; physical
rail voltage was not measured. This board-specific dependency was checked
against the matching J72 driver before the test. It is not a generic recipe
for other PMICs or panels.

With firmware, calibration, SPI timing and report configuration otherwise
preserved, the owner gesture capture contained 1,801 valid native frames:
1,209 empty, 542 with one finger and 50 with two. Nine press/release lifecycles
matched and no contacts remained down. A later visual Linux-input test
recorded 21 presses and 21 releases, including simultaneous contacts; the
owner confirmed screen mapping. These tests distinguish actual touch from
firmware startup alone.

A native contribution still needs bindings, compatible-selected behavior,
proper supply/clock ownership, firmware conversion and a clean cold boot
through Orchard's normal path. See the related [N61 touch record](n61-touch.md)
and [calibration notes](touch-calibration.md) for existing infrastructure;
J72 board values need their own evidence.

## Battery and charging findings

The kernel frontend owns UART5 while battery properties are read; no raw tty
reader runs beside it. Three bounded voltage reads initially agreed at
3,824 mV, and the volatile identity query returned `0x0545`. The frontend is
derived from the [Air 2 HDQ work](https://github.com/mattonik/ipad-nixos/tree/b94d42f78e04c5465e290340a5b6879bbc5956b6).

An exported-capacity discrepancy came from pairing uncompensated remaining
capacity with compensated full capacity. The local J72 experiment pairs
compensated remaining/full values, which agree with reported percentage on
the device. This does not establish physical battery health. Also, the gauge
can report `Full` while signed battery current is negative, so status alone
is insufficient evidence of charging.

A read-only PMIC observer found input suspend clear, a nominal 100 mA USB
input ceiling (`0x04c0 = 0x02`), and nonzero battery-current settings. The same
input ceiling persisted after moving to wall power while battery current
remained near -743 mA. The J72 configured battery-current ceiling is at
`0x04ce`; copying the Air 2 reference's `0x04cf` would read a different field.
These settings are not measurements of actual USB input or charge current.

A one-shot experiment then changed only the input ceiling on the same wall
source, after desktop, input and the host root were detached:

| Phase | Nominal input ceiling | Measured battery current |
| --- | --- | --- |
| Before | 100 mA | -764 mA |
| Trial | 425 mA (`0x04c0 = 0x1c`) | -423 to -400 mA across 12 retained samples |
| After restoration | 100 mA | -767 mA |

The trial used battery checks, one physical request, a 30-second restoration
timer and a separate rollback queue that never reads the gauge. Final state
reported `restored=1`, `restore_failed=0`, `error=0`; a separate snapshot
confirmed `0x04c0 = 0x02`. The exact restoration instant was not photographed,
and the complete wall RAM log was not retrieved. Screen photographs retain
the active setting, current range and restored result.

The reversible change reduced discharge magnitude by about 45-48%. It supports
an input-budget contribution to discharge, but battery current stayed
negative and actual USB input current was not measured. The powerboard USB
source's rating was unconfirmed. A later 850 mA comparison on a separate,
owner-rated 5 V / 1 A source has now run, as reported below.

**Sustained Linux charging is unqualified.** These are observations from
bounded development tests, not a charging policy or an instruction to write
PMIC registers. Follow the [charging bring-up guidance](charging/README.md)
for source identification, protections and qualification.

## 850 mA wall comparison: brief net charging observed

One 30-second, single-attempt test on the separate owner-rated 5 V / 1 A
charger changed the nominal input limit from 100 mA (`0x04c0 = 0x02`) to
850 mA (`0x3e`). The USB-backed desktop/root and touch worker were stopped
before the cable move. The owner confirmed advancing uptime on that charger
and pressed Home once after the baseline interval.

| Phase | Battery current |
| --- | --- |
| Same-source baseline | -766 mA |
| Trial, 12 retained samples | **+20 to +51 mA** |
| After automatic restoration | -765 mA |

The active photo shows the green screen, `Charging` and `0x04c0 = 0x3e`.
The final photo shows `used=1`, `active=0`, `armed=0`, `restored=1`,
`restore_failed=0`, `error=0`, and `0x04c0 = 0x02`. Temperature in the two
photos is 34.9 and 35.1 degrees C; reported charge stays at 91%. The owner
then confirmed iOS is visible and charging on the same wall source.

This demonstrates brief positive **net battery current**, with verified
restoration. It does not qualify sustained charging, a charge-level trend,
source detection, protections or desktop charging. Actual USB input current
and supply capacity were not measured; the exact restoration instant was
not photographed, and the full wall RAM log was not retrieved. Raw photos
remain private. The source snapshot still contains the tested 425 mA worker;
the 850 mA variant used for this result is not bundled in that snapshot.

Next: implement source-aware bounded charging, qualify a longer guarded
measurement and recovery, then proceed to Wi-Fi. No internal-storage writes
or host-kernel changes were performed.

## Recovery limits and remaining work

After a live Linux wall-charger-to-Pi return failed to enumerate, the owner
reported that the Pi hung and required a restart. Its crash journal was not
available; the cause is unresolved. Later Home-requested gadget rebinds
restored network access, but one was followed by failed serial access and
loss of network responses. Cached USB `configured` state also persisted on
wall power and did not establish source identity.

Current wall tests use screen evidence and return to iOS while still on the
charger before any Pi attachment. No live Linux USB-return fix is claimed.

Remaining J72 work includes normal-path driver/DT/recipe integration,
source identification and sustained charging, Wi-Fi, Bluetooth, audio,
suspend/resume, GPU acceleration and broader stability tests. Internal
storage installation and untethered boot have not been exercised. A future
device PR must test its exact revision, preserve driver attribution, express
hardware differences through match data/DT, and qualify shared changes on
the other affected devices under [CONTRIBUTING.md](../../CONTRIBUTING.md).
