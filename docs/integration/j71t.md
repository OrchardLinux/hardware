### Setup

Use a fresh clone of the **omarchy-a** workspace on `feature/j71t-integration`, in a new directory. Its `cli/` and `hardware/` submodules are pinned to the matching `feature/j71t-integration` commits of those repositories. The `./orchard` launcher only initializes missing submodules and never updates existing ones, so an older omarchy-a checkout (such as the one from omarchy-a#4) would quietly build with the old CLI and hardware.

Host requirements as in omarchy-a's `examples/minimal-boot/README.md`: uv, Git, a running native ARM64 Podman, palera1n and libusb; local Pongo builds need macOS with Xcode.

```sh
git clone --recurse-submodules -b feature/j71t-integration \
    https://github.com/OrchardLinux/omarchy-a.git orchard-j71t
cd orchard-j71t
git submodule status   # both lines without a leading - or +: the pinned commits are checked out
```

The workspace's `orchard.toml` defaults to `device = "j71b"`, so pass `--device j71t` to every build (or change `orchard.toml` locally).

### Building and RAM boot

```sh
cp -R examples/minimal-boot ../j71t-stage1   # BusyBox, USB serial root shell; edit its init (test plan, stage 1)
./orchard build ../j71t-stage1 --device j71t --modules
./orchard run ../j71t-stage1
```

`./orchard build` builds the kernel from `hardware/` (torvalds v7.3-rc1 plus the series from `hardware/kernel/series.py j71t`, DTB `s8003-j71t`), BusyBox, the loader and Pongo, and writes the payload to `out/` in the directory you pass. A directory holds your `init` and an optional `rootfs/` (`cli/docs/ram-development.md`). The serial shell is described in the example's README.

A RAM payload carries no firmware: stage the recipe outputs of `hardware/devices/j71t/firmware.json` under `rootfs/lib/firmware/` (`orchard_cli.recipe.run(recipe, read_input)` produces them from the 20H350 IPSW and the device's kernelcache). It also carries only BusyBox: stages 2 and 3 need `evtest`, `iw`, a Wi-Fi supplicant and `bluetoothctl` added under `rootfs/` (static aarch64 builds), or those checks move to the installed system after stage 4.

The kernel and m1n1 can also be built on their own from `hardware/` (`hardware/BUILD.md`; kernel builds run in Podman):

```sh
hardware/kernel/build j71t --output "$PWD/out/kernel"   # Image.gz, j71t.dtb, dtbs/, lib/modules
hardware/boot/m1n1/build j71t --output "$PWD/out/m1n1.bin"
```

Nothing is published yet: there is no J71t launcher release, so `./orchard install` and `./orchard launch` for J71t need locally built recovery and launcher assets (`hardware/BUILD.md`, "Shared launcher and publication").

## 2. Test plan

On an iPad6,11 (J71t). Go stage by stage and stop at the first stage that fails; send back what that stage asks for. Nothing before stage 4 writes to the internal storage. Your release 2 boot path stays available as a fallback; nothing here touches it.

You need the iPad in DFU mode, the workspace from section 1 ("Setup"), a USB-A to Lightning cable, and Wi-Fi credentials for stage 3.

### Stage 1: RAM boot, storage read-only (about 10 minutes)

Boot the RAM payload from section 1 ("Building and RAM boot"). Nothing in it mounts or writes storage. As a second guard, add this to its `init` right after the pseudo filesystems are mounted. NVMe probes asynchronously (ledger 3.7), so it waits for the devices instead of running once at startup:

```sh
# Fence every NVMe namespace and partition read-only once they appear.
(
    i=0
    while [ ! -e /sys/class/block/nvme0n1 ] && [ "$i" -lt 60 ]; do sleep 1; i=$((i + 1)); done
    sleep 2   # let the partition scan finish
    for d in /sys/class/block/nvme*; do
        [ -e "$d" ] && blockdev --setro "/dev/${d##*/}"
    done
) &
```

Orchard's recovery runtime does the equivalent in `runtime/j71b/phase2-hardware` (every partition, and every namespace except `nvme0n1`, read-only).

## 3. Questions

Most important first. The ledger item in parentheses has the context.

1. **Port 1 (Wi-Fi) sequence (2.3):** the integration brings port 1 up with the same sequence as port 0 (2.2), with Wi-Fi powered through `pci-pwrctrl`: up to two power cycles of the endpoint, each with up to two link attempts. Your validated runs used `round7` on port 1. Did you ever bring port 1 up with the reset/full-cycle sequence?
2. **Wi-Fi power (2.7):** does Wi-Fi come up powered through `pci-pwrctrl` (fixed regulator on PMU GPIO 14 with `off-on-delay-us = <100000>`) instead of the late-port `pwren-gpios` path? Stage 1.1 and 3.1 answer this.
3. **Shared MSI (3.5):** did a crawl ever happen on a cold boot, and is there a device result for "service every CQ on the shared MSI" (the patch notes say build-only)?
4. **PMU event line (6.1):** your DT uses AP GPIO 76 (level-low) for the D2365 event output on J71t (38 on J71b). Is that from the ADT, and the same on J71s and J72t?
5. **Touch ATN (8.1):** the J71T variant takes a falling edge on the ATN line (AP GPIO 65), reads `attn-gpios` to drain queued reports, and recovers from runtime errors with a bounded retry. Does the N1 keep ATN low while reports are queued, as that model assumes? And does it echo the report ID in E3 replies (the variant no longer checks byte 1)?
6. **HMB (3.3):** does the live ADT carry `nvme-mmu0` `sart-region` on every iPad 5 you've seen? Orchard's m1n1 fills the HMB from it.
7. **Touch analog supply (8.8):** where does D2365 register 0x31c bit 0 come from? The ADT only names `pmuL 0x21f`.
8. **Touch differences (8.1):** besides the HBPP version, MtCl/calibration upload, descriptors and timings, does anything in N1 differ from the J71b generation-1 runtime (the J71B paths in `kernel/patches/drivers/input/0001`)?
9. **Bluetooth module (15.3):** is your unit's module USI or MUR? The recipes install the USI patchram (FearA `5513d25b…` for J71t, FearB `85db6624…` for J72t); BlueTool also carries the MUR variants (`05bb2dd9…`, `557bc2ab…`). Can the ADT tell which module a unit has?
10. **ALS (9.3):** did you measure A1/A2 (CONTROL 0x02 vs 0x03; how the interrupt clears)? And the Smart Cover polarity (9.4)?
11. **Apple host grant (6.7):** which hosts sent it on your unit: only macOS, or also Windows/iTunes?
12. **USB host (7.5):** is the camera adapter's power handshake (-19 after charge10) understood? Once host mode works end to end (hub plus drive), it can be integrated on its own.
13. **Tunables (2.4):** are the PCIe tunables identical in another J71t, J71s or J72t live ADT? That would confirm they're SoC constants.

### Check 1: sequence differences found and fixed

PCIe, NVMe and DART: every register value and offset of the port bring-up, PHY-IP init, tunables, DART attach and ANS enable matched. These behavioural differences were fixed:

| Difference | Fix |
|---|---|
| The host probe waited for the Wi-Fi power control; a failure there aborted the bridge, NVMe included | Port 0 first, Wi-Fi power after; port 1 failures stay local |
| Port 0 had no retry | Two link attempts, then a full power cycle and one more bring-up |
| Port interrupts requested and enabled on S8003 | Not requested on S8003 |
| NVMMU init without the FIFO poll and `SART_CTRL = 0`; a missing HMB failed every port | Your order; a missing HMB only disables NVMe |
| Port stop without `port+0x8c = 0` and the LTSSMCTL readback | Restored |
| Wi-Fi REG_ON 100 ms off not guaranteed; one link attempt | `off-on-delay-us`; two power cycles |
| No 100 ms wait after CC.EN before the first CSTS read | Restored |

Touch, SPI and display: the protocol layer matched your driver (power-up, HBPP handshake, calibration and firmware upload at 0x10009000 with the 57016-byte packet in one transfer, register calibration, discovery and runtime framing, contact parsing). Fixed below it:

| Difference | Fix |
|---|---|
| S8000 SPI PIO slept the whole transfer time after one FIFO load (SCLK stopped about 44 ms mid-firmware) | Streams without the sleep |
| S8000 SPI register order never run on S8000 | Your order |
| ATN pin never configured as an input | `attn-gpios` restored |
| `ps_spi3` power-cycled per message | Runtime-PM reference held |
| No runtime error budget or recovery for touch | Retries, mask, delayed rearm |
| TX refill could overrun the RX FIFO | In-flight cap of 16 |
| E3 byte-1 echo check stricter than yours | Dropped for J71T |
| Display DART bypass check before retiring simpledrm missing | Restored, with a 100 ms flip timeout |

Two bugs found on the way: the touch IRQ disable depth after a failed resume, and `IRQCHIP_SKIP_SET_WAKE` missing from Apple pinctrl (every system suspend with wakeup buttons failed on all Apple pinctrl SoCs).

### Check 2: intended DT differences

Not described on purpose:
- SEP, `sep-shmem`, the GPU diagnostics node, and USB host mode (7.5).
- The DWI backlight's wide `0x20e200000` range: ours is Hoolock's node; the block init that needed it is deferred (9.7).
- The `adbe_boot_vram` reservation: m1n1 hands Linux only iBoot's usable range, and the framebuffer lies outside it.

Described differently:
- Binding renames and fallback compatibles (display pipe, UARTs, Bluetooth, gauge, SPI, touch, touch clock); an explicit AIC `interrupt-parent`.
- Five-cell DART windows with `#iommu-cells = <5>`; PCIe without clocks; `num-lanes`.
- Wi-Fi powered via `pci-pwrctrl` (`vdd-supply` instead of `pwren-gpios`), device-wake on the endpoint, a host-wake interrupt.
- ALS calibration via m1n1 instead of `firmware-name`; PMIC nvmem/rtc with `#size-cells = <1>` (5.2); `hs-switch-gpios` dropped (audio).
- The PMU event line `<&pinctrl_ap 76 IRQ_TYPE_LEVEL_LOW>` on `pmu_gpio`, which is now an interrupt controller (5.1); the charger requests its events from there (6.1).
- The display pipe holds `ps_disp0`/`ps_dp` with `apple,always-on`, as in your tree.
- The WLAN UART2 as Orchard's `apple,t8010-wlan-uart-provider` platform control (as on J71b) instead of a plain UART; Wi-Fi doesn't use its data path.

### Decisions already made (Orchard)

- **Charging: no undifferentiated 2.4 A.** Orchard grants input current only for an identified source:
  - Apple BrickID;
  - USB-C CC (1.5 A or 3 A);
  - BC1.2 CDP/DCP (1.5 A);
  - the Apple host grant.

  Anything else stays at 500 mA.
- **Charging: always the highest grant the source makes reasonable** (2026-10-28). Every source gets the maximum it states itself or that a spec covers, up to the board maximum:
  - the Apple host grant: whatever macOS offers, up to 2.4 A (6.7);
  - a 3 A Type-C advertisement: the board maximum, with no iOS-style clamp to 1.5 A (6.5);
  - an unidentified or unconfigured source: 500 mA (6.6).
- **Scope: everything in this integration** (2026-10-28). Audio (10), display (11) and the H.264 decoder (12) are integrated together with the base, each with a mainline-practice review of its own.
- **PMIC events: one shared D2365 event interrupt controller, in this integration** (2026-10-28). The PMIC/GPIO driver owns the read-to-clear event block and publishes events as ordinary IRQs. `apple_tristar_charger` (withdrawal path), the PMIC GPIO lines (Smart Cover halls) and later consumers request them. The charger is re-validated on J71b. Your findings go into the shared `apple_tristar_charger` (topic 6) as inputs: BC1.2 results kept across the cable's ID exchange, an enumerated host, CC through the USB-C to Lightning cable.

### Orientation: what changed since your PR, and why

Your PRs were built for the repository as it was on 2026-10-27: a Hoolock fork plus one large per-device kernel patch, per-device recovery, runtime and CLI packages. Since then the hardware repository has moved to a layered stack, so that every Linux-on-Apple-A-chip effort can contribute to one platform instead of a fork per device:

- **Kernel:** torvalds v7.3-rc1, then ordered patch layers: Hoolock (verbatim, tree-hash verified), Paul Praschl's series (replayed with his authorship), `drivers/<subsystem>/` (driver code, whoever needs it first) and `devices/<soc>/` (device trees). One kernel and config for every device.
- **Device data:** a descriptor per device (`devices/<device>/device.toml`, with a feature matrix and caveats) and a declarative firmware recipe (schema 2: inputs from the public IPSW, steps from a fixed vocabulary, every output pinned by hash).
- **Boot and install:** one m1n1 patch fills per-unit data from the ADT on every device. The recovery, runtime, CLI adapter and distribution release are device-generic.

The rules that explain most of this ledger:
1. **No device gates in shared drivers.** `of_machine_is_compatible("apple,j71t")` and similar checks become match data or go away.
2. **Per-unit data comes from the live ADT via m1n1:** MAC and Bluetooth addresses, Wi-Fi, touch and ALS calibration, NVMe HMB. Nothing private is packaged.
3. **Storage safety lives in the installer and runtime,** not in the kernel (Orchard removed its own J71b kernel fence for the same reason).
4. **SoC behaviour goes in match data, not DT properties:** tunables, NVMe mode, lane configuration.
5. **No bring-up scaffolding in the final stack:** diagnostics, staged parameters, debugfs triggers and kexec paths stay in your research tree.
6. **Orchard boots cold through m1n1 and never kexecs,** so warm-boot handling isn't needed.

Your history stays intact: each integrated patch keeps you as author and names the original commits (see "Attribution"). Several of your findings apply beyond the iPad 5 and are being tested on the iPad 6 ("J71b RAM test" below).
