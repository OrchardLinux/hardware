# iPad Air 2 (J81) integration

This branch carries Martin Puškáč's iPad Air 2 work (mattonik/ipad-nixos `b94d42f`, handed to Orchard by micro23 in micro23/ipadair2-omarchy `7ea2b2b`) onto Orchard's layered stack. Orchard has no iPad Air 2, so nothing here has run on one yet. This document is for whoever tests it on a J81: how to run it, what to send back, and what changed against the work it comes from.

## 1. Test it

You need the iPad Air 2 (Wi-Fi, J81) in DFU mode, a Mac or Linux host with [uv](https://docs.astral.sh/uv/), Git, palera1n, libusb and a running native ARM64 Podman, and a USB cable. Nothing is installed on the iPad and nothing touches its storage: the image runs from RAM, and the iPad's NVMe is set read-only as soon as it appears.

```sh
git clone --recurse-submodules https://github.com/OrchardLinux/omarchy-a.git orchard-air2
cd orchard-air2
git -C hardware fetch origin feature/air2-integration
git -C hardware switch -c feature/air2-integration --track origin/feature/air2-integration
```

Put your Wi-Fi network in `examples/hardware-check/rootfs/etc/wpa_supplicant.conf` (WPA2; the file stays out of git):

```
network={
	ssid="your network"
	psk="your passphrase"
}
```

Then build, boot and check:

```sh
./orchard build examples/hardware-check --device j81 --modules --firmware
./orchard run examples/hardware-check
screen /dev/cu.usbmodem* 115200          # Linux: screen /dev/ttyACM0 115200
```

The first build downloads the iPadOS 15.8.8 IPSW once (about 5 GB, and it needs about 10 GB free to unpack) for the Wi-Fi firmware and builds the 4 KiB-page kernel; later builds reuse both. With `wpa_supplicant.conf` in the image, the Wi-Fi checks run by themselves at boot. At the shell, run:

```sh
hardware-check
```

It takes about three minutes. Then press a few buttons with `hardware-check keys`. Send back `/run/hardware-check.txt` and `/run/dmesg.txt`: paste them from the serial shell, or fetch them over USB networking from `http://10.71.0.1:8080/` (your host gets 10.71.0.2).

What to expect:

| Check | Expected |
|---|---|
| Storage | SKIP (no storage driver for the A8X yet) |
| PCIe | `14e4:43a3` bound to `brcmfmac` |
| Wi-Fi | The firmware version in the log; networks found; associated; DHCP; gateway ping |
| Battery | 10 readings without errors |
| Display and backlight | simpledrm or `fb0`; the backlight follows writes, if the PMIC backlight is present |
| Kernel log | No DART faults, warnings or oopses |
| Keys | Input events from the buttons |

If Wi-Fi fails, the kernel log is the most useful thing to send; section 3 lists what to look for.

## 2. What exists

The branch `feature/air2-integration` of OrchardLinux/hardware:

- **Kernel**, 15 patches: 13 for the shared drivers, already on main (`kernel/patches/drivers/*`), and the 2 device trees on this branch (`kernel/patches/devices/t7001/`):
  - PCIe: the A8X host as a T7000 variant of `apple-h9p`. Martin's register sequence, Gen1 limit, DBI overrides, tunables and MSI layout are match data. Wi-Fi power (REG_ON, device-wake) goes through `pci-pwrctrl-apple-wifi`.
  - DART: T7000 hardware data; the error reflector written first, as in iOS 8.1.
  - brcmfmac reads the BCM4350 OTP, so it picks the unit's Apple NVRAM itself, without a separate radio-ID kernel.
  - The D2207 PMIC GPIO for Wi-Fi REG_ON.
  - The T7000 UART binding.
  - Device trees: UART5, the PCIe DART and the PCIe controller on T7001; Wi-Fi and the battery gauge on the iPad Air 2. `brcm,board-type` is the ADT's Wi-Fi module: `rieslinga` on J81, `rieslingb` on J82.
- **Device data:** `devices/j81` and `devices/j82`. Platform `apple-4k` (A8X has no 16 KiB pages), RAM boot only, every feature `untested` or `missing`.
- **Firmware recipes:** the BCM4350 C2 firmware of the device's module from iPadOS 15.8.8, every NVRAM variant included.
- **m1n1:** no change needed. It fills the Wi-Fi MAC through the `wifi0` alias and finds no NVMe HMB node to fill.

Every patch derived from Martin's work keeps him as author and names his original patches in its `[Orchard: …]` note. Each was reviewed against Orchard's rules: shared drivers extended, no device gates, no diagnostics or module parameters, SoC behaviour in match data.

## 3. Differences from the work it comes from

An independent comparison against Martin's final state found no difference likely to break Wi-Fi: every register value, mask, write order and delay on the PCIe path matches. The following differ on purpose and are what to look at if Wi-Fi fails, most likely first:

1. **DART leaf protection bits.** Orchard's leaves keep read/write permission bits; Martin's had none. One field switches (`no_perms` in `apple_dart_hw_t7000`). Symptom if wrong: DART read or write faults when Wi-Fi starts.
2. **No double mapping.** Martin's runs mapped every DMA page twice (rebased and raw). Orchard maps once, rebased, which his own fault analysis points to. Symptom if wrong: DART faults at addresses above 0x80000000.
3. **DART setup checks.** The translation setup reads back what it wrote and blocks DMA if the hardware disagrees. Symptom: "translation setup … failed" or "blocking DMA" in the log.
4. **Device-wake timing.** pwrctrl raises device-wake before link training; Martin raised it after the link was up. Symptom: the link comes up but brcmfmac's firmware download or first command times out.
5. **OTP reading.** brcmfmac reads the BCM4350 OTP, which Martin's path never did, and sets its select bit. Symptom: an OTP error, or a request for an unexpected NVRAM name.
6. **Power domains.** The PCIe node holds all three PCIe power domains instead of leaving two to `pd_ignore_unused`. Symptom: the link doesn't come up.
7. **Firmware.** iPadOS 15.8.8's BCM4350 firmware is newer than the iOS 8.1 firmware of Martin's runs. If brcmfmac fails at firmware load or init, the firmware source is revisited.

Not taken: the storage driver (ANS1), touch, Bluetooth, the charger, audio. They weren't validated in Martin's port and come later.

## 4. Questions

1. Which Wi-Fi chip revision does your unit report (`brcmfmac` logs `BCM4350/…`)? The recipes install the C2 firmware; iPadOS also carries C4 and C5.
2. Which NVRAM does brcmfmac request (module, vendor, version in the log)? Martin's unit used CIDR/u/2.1.
3. Does the J82 (cellular) behave the same, if you have one?
